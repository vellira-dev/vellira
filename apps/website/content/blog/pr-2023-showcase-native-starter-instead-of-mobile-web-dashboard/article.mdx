A product website can easily drift away from the product it is supposed to explain. That risk is especially high when a React website needs to demonstrate a React Native application: rebuilding the mobile UI in web components is convenient, but the preview can quietly become a second implementation with different states, different behavior, and different maintenance costs.

Vellira took a narrower approach for its Native Starter showcase. The desktop demo remains the real React Web dashboard, while the Mobile preview is generated from the canonical Expo Native Starter source and adapted only at the browser boundary. A follow-up change then synchronized the isolated mobile preview with the website's active theme.

The goal is not to pretend that a browser iframe is an iOS or Android runtime. The goal is to keep the website preview tied to the same product source that developers actually receive.

## The problem: a mobile preview can become a fork

Before [PR #2023](https://github.com/vellira-dev/vellira/pull/2023), the homepage Mobile state could be represented by narrowing the web dashboard or by maintaining a separate hand-written approximation.

Both options create the same architectural problem: the marketing preview can evolve independently from the Native Starter.

That makes seemingly small changes expensive. A settings screen may be updated in Expo but not on the website. A notice component may gain a new state in the starter while the preview keeps the old one. Design tokens can remain similar while interaction semantics diverge.

For Vellira, the useful constraint was stronger:

> The Native Starter remains authoritative. The website may project it into the browser, but it should not become a second source of product UI.

That constraint determines how the preview is built and what it is allowed to claim.

## Generate the browser preview from the canonical Expo source

The Mobile showcase imports a web-local copy of selected Native Starter source: the app shell, settings UI, workspace notice, and pure project UX modules.

That copy is not maintained manually. The repository exposes a synchronization step:

```text
node scripts/website/sync-native-starter-preview.mjs
```

The same script also supports a check mode so CI can verify that the browser projection still matches the authoritative Expo source.

This matters because generated source changes the review question. Instead of asking whether two implementations still look similar, maintainers can ask whether the website projection is still mechanically synchronized with the source it represents.

The original Expo app remains unchanged. Website-specific compatibility stays outside the Native Starter rather than leaking browser constraints back into the package developers actually use.

## Adapt only the browser-specific boundaries

A real React Native application cannot simply be imported into a Next.js website unchanged. Some dependencies are runtime-specific, and resolving the separate Expo project's dependency tree directly from the website can create bundler and parser problems.

Vellira limits the browser bridge to a small set of explicit substitutions:

- Expo Blur
- Safe Area handling
- AsyncStorage

Everything else in the projected product surface stays as close as possible to the canonical Native Starter source.

This is an important boundary. The browser adapter layer exists to make the preview renderable; it is not permission to reinterpret the product behavior.

It also avoids coupling the website to the Expo project's nested `node_modules`. That keeps Turbopack from having to consume React Native-specific dependency internals that the marketing site does not own.

The result is a narrower integration surface: canonical product source on one side, a few browser adapters on the other.

## Keep web and native demos separate

The desktop and mobile states intentionally represent different runtimes.

The desktop view continues to show Vellira's React Web dashboard. The Mobile view shows the Native Starter projection.

That distinction is more useful than forcing both tabs through one implementation. Cross-platform consistency does not require the web dashboard to impersonate the mobile application, and it does not require the mobile preview to inherit web-only structure.

Instead, the preview communicates a more accurate product contract:

```text
Desktop -> React Web product surface
Mobile  -> Expo Native Starter source projected into the browser
```

The website can compare the two without erasing the runtime boundary between them.

## Synchronize theme state before the preview mounts

[PR #2078](https://github.com/vellira-dev/vellira/pull/2078) exposed a second problem.

The Native Starter preview runs in an isolated iframe. After the first version landed, changing the website between Light and Dark mode did not necessarily update the embedded preview because the Native Starter maintained its own persisted appearance state.

The fix treats theme synchronization as an explicit boundary crossing.

The parent website passes its resolved theme into the preview URL. The isolated browser demo initializes the Native Starter's theme storage before mounting the canonical application.

That ordering is important. If the app mounts first and theme state arrives later, the preview can briefly render with stale appearance or preserve a previous iframe state.

The mapping also preserves the difference between website-level and native theme vocabulary:

- website `light` -> native Light
- website `dark` -> native Dark
- website `high-contrast` -> native `highContrast`
- website `system` -> the website's resolved Light or Dark value

The Native Starter source still owns its theme behavior. The website owns the initial bridge that tells the isolated demo which state it should begin with.

## Test the synchronization contract, not just the screenshot

A preview like this has several failure modes that a static screenshot would not catch.

The repository therefore checks the relationships around the showcase: that the Mobile state uses the Native Starter path rather than the React Web dashboard, that generated source remains synchronized, and that the resolved website theme is bridged before the embedded app mounts.

Those checks are valuable because the maintenance risk is structural.

A developer can make the preview look correct locally while accidentally breaking source parity. A theme can appear correct on first load while failing after Light -> Dark -> Light switching. A refactor can keep the iframe visible while reconnecting it to the wrong product surface.

The useful tests encode those boundaries so the preview is reviewed as an integration, not as a decorative mock.

## Do not overclaim what the browser proves

There is still a hard limit: a browser preview is not native runtime evidence.

The website can demonstrate the Native Starter's product structure, content, theme states, and much of its interaction model. It cannot prove that iOS blur, Android rendering, native gestures, safe-area behavior, or platform-specific performance are identical to the real Expo application.

Vellira keeps that limitation explicit.

This is important for any design system that supports both React and React Native. A cross-platform demo should make shared product semantics easier to inspect without collapsing the distinction between runtime implementations.

The browser projection is useful because it is synchronized with native source, not because the browser has become native.

## A practical maintenance rule

When the Native Starter changes, the website preview should be treated as a generated consumer of that change.

A useful review sequence is:

```text
1. Change the canonical Expo Native Starter.
2. Regenerate the website projection.
3. Verify source parity.
4. Review the small browser-adapter boundary.
5. Test desktop/mobile selection and theme synchronization.
6. Confirm that the preview still avoids claims that require a real native runtime.
```

This keeps the expensive part of cross-platform maintenance in one place: the actual product source.

The marketing site then becomes a constrained projection of that source rather than another implementation that has to be remembered during every product change.

## Why this matters for Vellira

Vellira's broader cross-platform model is based on sharing product semantics while allowing web and native runtimes to stay native.

The Native Starter showcase applies the same idea to documentation and product presentation.

The site does not need to duplicate the mobile application to explain it. It needs a trustworthy way to project the canonical source, isolate the few browser-only substitutions, and make the remaining runtime limits visible.

That is a smaller promise than "the browser preview is the native app."

It is also a much more maintainable one.
