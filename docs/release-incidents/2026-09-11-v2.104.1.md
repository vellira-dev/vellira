## Failure boundary

plugins, and tag creation. All six npm publish commands then ran. The icons
publish command returned success at `2026-09-11T22:38:13Z`, including signed
provenance and transparency-log index `2799283034`. Its eight registry reads
continued returning E404, and the package plugin failed at
`2026-09-11T22:40:37Z`. The GitHub plugin and every version-sync step were never
run.

npm records the icons publication at `2026-09-11T22:42:21.172Z`, about 247
seconds after the successful publish command returned. The first fatal error was
therefore a read-after-write visibility timeout, not a failed publish or
concurrency queue truncation.

## Root-cause conclusions

1. The six-package contract first becomes complete at `2.19.6`. The only raw
   version-set divergence is `2.18.4`, before that contract: core exists while
   the other five packages do not.
2. No repeating successful/failing package subset exists. The two modern
   incidents affected different packages: react-native at `2.103.4` and icons
   at `2.104.1`.
3. The incidents do not correlate with a fixed concurrency wave. Three workers
   each drain the shared queue, all six publish commands were attempted in the
   failed run, and the affected packages occupied different queue positions.
4. npm's private Trusted Publisher configuration cannot be enumerated through
   the public registry. Nevertheless, npm accepted all six `2.104.1` OIDC
   publications from the same pinned `release.yml` workflow and returned valid
   provenance, which rules out a package-specific trust mismatch for this run.
5. The package dependency graph is not the cause. Publishing a tarball does not
   resolve its declared dependencies. Topological waves are therefore not
   required for npm acceptance, although the permanent all-six verification
   gate now prevents downstream release completion until every dependency
   package is visible and verified.
6. A successful publish can be followed by a registry/provenance visibility
   timeout. That is exactly what happened to icons at `2.104.1` and to
   react-native at `2.103.4`.
7. A thrown worker exception could previously reject `Promise.all` and abandon
   queued work. The publisher now converts an unexpected per-package exception
   to a failure summary, continues draining the queue, and finally verifies the
   exact six-package set. Ordinary publish/verification failures already
   returned summaries and did not poison another worker.
8. Earlier tags can survive failed publication because semantic-release creates
   the tag before its publish plugins run. In the failures reviewed here, a
   GitHub Release was not created. No successful six-package-era Release run was
   found with a genuinely partial npm version set; a tag or GitHub Release alone
   is no longer accepted as completeness evidence.
9. The old plugin treated the exhaustion of a short, attempt-count-driven
   read-after-write retry window as a final publish failure. It did not perform
   a fresh all-six completeness pass after the workers finished. Registry
   visibility now has an explicit bounded six-minute default deadline,
   progressive sleeps are truncated to that deadline, and the final gate
   independently queries all six exact versions.
10. A release is successful only when all six exact npm versions and expected
    provenance are verified, the immutable tag and matching GitHub Release
    exist, and canonical repository version synchronization has completed.
