# 2026-09-28 v2.124.0 npm visibility incident

## Summary

Release v2.124.0 created its immutable tag at commit
`0b4b09de9ed3b3918dec32b5cd87c28793d9f138` and npm accepted all six package
publish commands. Five packages became readable and provenance-verifiable within
the normal verification window. `@vellira-ui/core@2.124.0` did not: npm
continued returning `E404` from the read path after the successful publish
command and provenance submission.

The release therefore failed closed before GitHub Release creation and before
the version-sync PR. The next push was stopped by the release-state guard because
`package.json` remained at 2.123.7 while the reachable immutable tag was
`v2.124.0`.

## Evidence

The release log recorded:

- `npm publish` success for `@vellira-ui/core@2.124.0`;
- provenance publication to the transparency log;
- repeated `npm view` `E404` responses for the exact version;
- one per-package visibility window followed by a second all-package
  completeness window;
- final failure before post-release repository synchronization.

Manual recovery later found all six exact npm package versions present with
verified provenance, including `@vellira-ui/core@2.124.0`. Its recovery plan
contained no package publication. Recovery created the missing GitHub Release
and version-sync PR #1373; #1373 then synchronized repository manifests to
2.124.0.

## Root cause

The release pipeline coupled npm mutation and registry visibility twice:

1. each successful publish worker waited for its package to become visible;
2. after all workers completed, the all-six completeness gate repeated the same
   bounded verification.

This created two sequential visibility windows while also holding publish
workers during npm eventual consistency. A package accepted by npm could still
produce a partial-release incident solely because the registry read path lagged
longer than both local windows.

## Correction

Normal release now separates mutation from observation:

1. publish all six packages with bounded mutation retries;
2. fail immediately on a true publish mutation error;
3. do not block individual normal-release workers on registry visibility;
4. verify all six exact versions concurrently under one shared absolute
   completeness deadline;
5. require integrity, tarball metadata, and provenance before semantic-release
   may continue to GitHub Release creation.

The normal completeness budget is 20 minutes by default through
`VELLIRA_RELEASE_COMPLETENESS_TIMEOUT_MS`. The six-minute
`VELLIRA_RELEASE_VERIFICATION_TIMEOUT_MS` remains the stricter per-package
budget used by recovery when it must publish a genuinely missing package.

## Safety properties retained

- immutable tags are never deleted or moved;
- a successful publish command alone never completes a release;
- provenance remains mandatory;
- the release-state guard still blocks the next release while external state is
  ahead of repository manifests;
- recovery remains the authority if the shared completeness deadline is
  exhausted.
